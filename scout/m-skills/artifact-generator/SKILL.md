# LISA Artifact Generator

## Purpose

Produce a customer-ready artifact set from completed LISA lifecycle stages:

1. `artifacts\solution-document.md` — a concise, customer-shareable solution document that synthesizes the decisions and outcomes worth the customer's time.
2. `artifacts\lisa-execution-tree.html` — a self-contained execution tree showing every LISA stage, its status, run ID, duration, source Markdown, and core artifacts.
3. `artifacts\solution-architecture.png` — a customer-named copy of the current validated architecture render when available.
4. `artifacts\solution-sequence.png` — a customer-named copy of the current validated sequence render when available.
5. `artifacts\artifact-generation-manifest.json` — the terminal hash inventory for the complete generated set.

The generator is read-only with respect to upstream stage folders. It never changes requirement, classification, design, build, evaluation, or optimization evidence.

When invoked by `cad-orchestrator`, follow `..\workflow-checkpointing.md`. Start the `artifacts`
stage when the `ART-*` ID is assigned; checkpoint input snapshot, render, validation, and publication
boundaries. Commit `artifact-generation-manifest.json` only after every listed artifact hash is final.

## Mandatory config-first path resolution

The first automation step is always to read:

```text
<path-to>\lisa-config.json
```

Invoke the packaged script with the config file, never with an output directory:

```powershell
python "<skill-dir>\scripts\generate_artifacts.py" --config "<project-root>\config\lisa-config.json"
```

`lisa-config.json` must contain `basePath`. The generator reads only `<basePath>\output\analysis`, `classification`, `design`, `build`, `evaluation`, and `optimization`, and writes only `<basePath>\output\artifacts`.

Use an IANA `timeZone` value in the config when generated timestamps must follow a specific business timezone:

```json
"timeZone": "Asia/Kolkata"
```

Accept absolute or config-configured `basePath`; reject caller-supplied child paths and stage paths outside that base.

## Current lifecycle stages

Resolve these paths beneath the config-selected output root:

| Order | Stage | Relative directory | Narrative inputs |
|---:|---|---|---|
| 1 | Requirement Analysis | `analysis` | Latest `requirement-analysis_*.md` |
| 2 | Complexity Classification | `classification` | Latest `complexity-classification_*.md` |
| 3 | Solution Design | `design` | Current design pointer, design model, diagrams; consume current Markdown if present |
| 4 | Agent Build | `build` | `agent-build-report.md`, `agent-instructions.md` |
| 5 | Agent Evaluation | `evaluation` | `evaluation-run-report.md`, `deployment-gate-summary.md` |
| 6 | Agent Optimization | `optimization` | `optimization-run-report.md`, current `rounds\round-NNN\round-report.md` |
| 7 | Artifact Generation | `artifacts` | The two final files generated by this skill |

Ignore hidden working directories and every `legacy` tree. Never read a previously generated `solution-document.md` as source input.

## Source-of-truth precedence

1. **Narrative and decisions:** current stage Markdown.
2. **Run identity, status, timing, and artifact integrity:** current manifests, run reports, current pointers, and state JSON.
3. **Architecture images and component model:** `design\current-design.json` and its current artifact directory.

Do not invent missing duration data. Display `Not recorded` when no supported start/end or explicit duration exists.

## Customer-shareable solution document

The solution document is an external-facing deliverable, not an internal evidence dump. Include only information that helps the customer understand the business need, proposed solution, delivered state, readiness, material risks, and next decisions.

`solution-document.md` must include:

- Executive summary and current readiness.
- Customer, solution name, platform, delivered agent, and deployment status.
- Customer-relevant lifecycle outcomes and stage durations.
- Problem, current state, desired future state, goals, success criteria, business metrics, integrations, agentic behavior, delivery phases, and material gaps from Analysis Markdown.
- Complexity, selected Microsoft platform/harness, rationale, and material architecture implications from Classification Markdown.
- Current architecture and sequence diagrams from the Design pointer.
- Designed component summary.
- Delivered scope, live status, channels, knowledge, runtime controls, and customer-visible capabilities.
- Evaluation totals, deployment decision, and concise descriptions of unresolved customer scenarios.
- Optimization outcomes, retained improvements, rollbacks, deferred work, and final state.
- Explicit target-state versus implemented-current-state distinction.
- Customer-relevant security, governance, deployment, operational, and ALM considerations.
- Known gaps, customer impacts, recommended next actions, and links to customer deliverables.

Do not include internal run IDs, requirement/evidence IDs, agent/environment GUIDs, hashes, absolute paths, raw instructions, full test prompts/responses, screenshot/evidence paths, source registers, package internals, or exhaustive component inventories. Remove internal traceability markers from imported prose and demote headings so the final document remains structurally valid.

## Required execution-tree HTML

`lisa-execution-tree.html` must be self-contained and include:

- The mandatory Clawpilot light/dark theme detection and variables.
- A sequential LISA lifecycle tree.
- Stage status, run ID, duration, timing basis, Markdown source count, and core artifact count.
- Expandable core-artifact lists with portable relative links.
- Total tracked duration and a clear count of stages with unrecorded duration.
- Search and expand/collapse controls implemented without external libraries.
- No external scripts, styles, fonts, images, network calls, or browser storage.

All colors must use the packaged Clawpilot `--cp-*` variables. Use Segoe UI/Aptos typography.

## Publication and validation

The packaged `resources\artifact-contract.json` is validated against the shared local-skills `artifact-contract.schema.json` before generation. It is the authority for the lowercase `artifacts` root, required files, optional diagrams, naming patterns, and statuses.

Write every artifact generated by this skill atomically under the single lowercase folder:

```text
<resolved-output-root>\artifacts\solution-document.md
<resolved-output-root>\artifacts\lisa-execution-tree.html
<resolved-output-root>\artifacts\solution-architecture.png
<resolved-output-root>\artifacts\solution-sequence.png
```

Do not leave generated copies in the resolved output root or any stage folder. After successful validation, remove obsolete root-level copies previously produced by this skill.

The packaged generator must verify:

- Config-first relative output containment.
- Required upstream stage directories.
- Every available current stage Markdown was read and appears in the source register.
- Legacy and hidden Markdown were excluded.
- Design links resolve beneath the output root.
- Stage duration is explicit, timestamp-derived, generator-measured, or `Not recorded`.
- The customer solution document contains no internal IDs, hashes, absolute paths, raw instructions, full test transcripts, or evidence registers.
- HTML contains all seven stages, the theme contract, and no external dependencies.
- Both output files are non-empty and atomically published under `artifacts`.

The skill is complete only when the command exits successfully and prints a JSON result with both output paths.
